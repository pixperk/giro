02The model

Four ideas carry the rest

Everything above is these four, and nothing else.

A posting names both sides

One amount, one asset, a source and a destination. No debit flag, no sign. An unbalanced entry is not something the shape of the data can express, so there is nothing to check.

Volumes, not balances

Each account holds input and output, both only ever increasing. Balance is the difference, computed on read. The database does the addition, so nothing read can become something written.

The log is the truth

Every change appends a SHA-256 entry chained to the one before. The tables are a projection of it, kept because replaying from zero on every read would be absurd. If they disagree, the log is right.

Nothing recorded ever changes

A mistake is corrected by appending its inverse. Triggers refuse an edit, a delete, and a truncate — against raw SQL, not just against the application.

Where money comes from

Every posting needs two sides, so the first deposit needs a source. Every account is empty and the money is coming from outside a system that is closed by construction.

world is that outside: a bank, a card network, somebody's pocket. It is allowed a negative balance, and by default it is the only account that is.

Its balance is a measurement. At −$500 it reads: five hundred dollars entered this ledger and have not left. For a wallet product that number is your total customer liability, and it should match your bank.

Splitting it per counterparty — external:lp:kraken:USD — makes each edge a balance you can compare against that counterparty's own statement. That is what reconciliation needs.

Two kinds of time

A settlement file arrives Thursday describing Tuesday's wire. So every transaction carries two timestamps: when it happened, and when we found out.

Mon 09:00wire leaves, per the bankeffective
Thu 14:20file arrives, we record itrecorded

"What was the balance on Wednesday" therefore has a real answer that changes when the file lands, and giro keeps both orderings so it can give you either. Ask with ?at=.

Anything ingesting settlement files from the outside world needs this, and it cannot be added later: it changes what every movement has to record.

One transaction, in full

Both postings land or neither does. timestamp is when it happened; when it was recorded is the server's business and it keeps both.

Three headers worth knowing

Idempotency‑KeyReplaying the same key returns the original transaction rather than committing a second one. A retry after a timeout is safe, which is the only way a payment client can be written.
?dryRun=trueRuns the whole commit path — locks, guards, balances — and rolls back. It answers “would this be refused” without a race between asking and doing.
?at=On any balance read: as of an effective date. The answer changes when a late settlement file lands, which is correct.

A refusal is a 4xx naming the account, the asset and the amount it would have held. Nothing partial is written, and the log has no entry for it: a refused transaction did not happen, rather than happening and being undone.

Amounts are integers in the asset's minor units, and USD/2 carries its own scale — so 12500 is $125.00 and there is no float anywhere on the path.

05Enforced below the application

What the database refuses

Every rule below is a Postgres trigger or constraint, not a Go check. The distinction matters because the thing that eventually writes to your ledger by hand, at two in the morning, in psql, is not going to go through your Go code.

RefusedMechanismBecause
Value appearing or vanishing deferred constraint trigger Every account summed, per ledger and per asset, is zero. Deferred because it can only be true at the end of a transaction — a posting is two half-truths and the check has to wait for both. A row trigger cannot see this, and neither can a statement trigger.
A volume going down before update input and output are monotonic. A correction that reduced one would be indistinguishable from money never having moved.
Editing or deleting a transaction, a posting, a log entry before update/delete The book is append only. Corrections are appended as their inverse, which leaves the mistake and the fix both visible.
truncate before truncate Truncate fires no row triggers at all, so append-only enforced only per row is a door with a hole beside it. This is its own statement-level trigger for exactly that reason.
An overdraft before insert/update An account cannot go negative unless it was explicitly allowed to, and that permission is set from Go, not over HTTP. Also the reverse: an account can be barred from going positive, which is how a pure-outflow account stays one.
An unregistered asset foreign key USDD/2 is a perfectly well formed asset that is not the one you meant. Unchecked, it becomes a second currency holding real money, and conservation passes because each pile balances on its own.
Re-registering an asset at a new scale before update/delete It would silently reinterpret every amount already recorded in it. A restatement of the whole book, wearing the clothes of a config change.
A counter going backwards before update Transaction and log ids would be reused, and a hash chain whose ids repeat cannot be verified.

A trigger the owner can turn off is a comment

A table's owner may disable its triggers. So if the serving process connects as the role that owns the schema, every rule above is advisory — correct, documented, and one alter table away from gone.

just db-app-role creates giro_app, which holds column-scoped grants and cannot log in, and giro_service, which logs in and inherits them. Between them: they can move money and cannot change the rules money moves under.

just privileges asks the database rather than the config. owns_tables f is the line that matters — it is the difference between a guard and a comment.

The test suite runs twice, once as the owner and once as giro_app. The tests that skip under the second run are exactly the ones that have to damage the book to prove a guard catches it — they cannot run as a role that is unable to do the damage.

06Against the outside world

Reconciliation

Every check above proves the book agrees with itself. None of them can tell you the money is actually in the bank — only the bank can answer that, and recon is the layer that asks.

The boundary is an account

Instead of one world for everything outside, give each counterparty its own edge: external:bank:northwind:USD, external:lp:kraken:USDT.

Each of those balances is then a claim about one real relationship, comparable against one real statement. Money entering the ledger crosses exactly one of them, which is the property that makes the comparison meaningful.

An account may only go negative if somebody said it could, so a boundary account is declared rather than named into being: giro account allow-negative main external:bank:northwind:USD USD/2, or SetAllowNegative from Go. Value cannot cross inward at an edge nobody opened.

The prefix is configuration, not a rule. Config.BoundaryPrefix defaults to external: and your naming is your own.

A source is an interface

A Record is one statement line: an id, a reference, an asset, a positive magnitude, a direction, and the raw bytes it came from. A bank adapter, an exchange adapter and a chain indexer all reduce to that.

No provider ships here. A ledger that ships a Kraken client has stopped being a general ledger. What ships is the interface, and a worked adapter in the tests — which is what proves the interface is sufficient rather than merely plausible.

Four steps, none of which move money

  1. Register the source once, so its lines have somewhere to live.recon.Register(ctx, db, "main", src)
  2. Pull or ingest its lines. Staging is idempotent on the source's own line id, so an ingest that timed out halfway is safe to retry — a second run of the same file stages nothing new.recon.Pull(ctx, db, "main", src, since)  ·  recon.Ingest(ctx, db, "main", id, records)
  3. Match lines against movements. Idempotent, so it belongs on a schedule.recon.Match(ctx, db, "main", cfg) → Summary
  4. Look at what did not match. That queue is the output. Nothing here writes a posting, and nothing corrects the book.A reconciler that could correct the book would be a second way for money to move, and the entire value of the layer is in having an independent opinion.

It matches movements, not transactions

A statement line is one account, one asset, one amount, one direction — which is exactly what a movement is. A transaction can be two of those at once: a conversion moves stablecoin one way and dollars the other, and has no single amount to compare a line against.

Two rules, both conservative:

exact_refOne line, one movement carrying the same giro/external.ref, same direction. Amounts inside tolerance match; outside it the pairing is still recorded, flagged as a variance.
consolidated_refOne line against several movements sharing a reference — a batched payout arriving as one wire. They must sum exactly. If they do not, it is indistinguishable from a coincidence and is left alone.

The reference lives in metadata rather than in the reference field, because several movements can share one and a transaction reference is unique per ledger.

Unmatched is four problems

Collapsing them into one number hides the fact that four different people fix them.

no_referenceThe source gave no match key. A source configuration problem, not a ledger one.
reference_not_foundA good reference naming nothing here. Either they recorded something we did not, or we have not recorded it yet.
reference_ambiguousIt resolves to several movements that do not sum to the line.
movement_already_matchedAn earlier line from this source claimed it. Two lines competing for one movement.

And the level above lines. CompareBalance asks a BalanceSource what it holds and compares it to the boundary account. It catches the failure line matching cannot: a movement neither side ever reported.

That balance means the net position across the edge, from our side — which is a different query for a chain, an exchange and a bank, and is the adapter's job to get right.

giro verify --recon-after=4h folds this into the same run as everything else: a line staged longer than that without matching becomes a finding, and the exit code carries it.

07Deliberately absent

What has no API, and why

A good deal of what giro does is reachable only from Go. None of it is an oversight, and the reasons differ.

CapabilityWhereWhy not over HTTP
Account bounds,
closure		 library cli These are the switches that turn the guards off. An endpoint letting a caller mark its own account unbounded is not an API, it is a hole in one — the overdraw guard is the thing standing between a bug and minted money, and permission to disable it should not travel over the same channel as the requests it protects against. giro account reaches the same database with the same role, and no listener in front of it.
The nine checks library cli Each is a full pass over a table. Behind an endpoint they are a denial of service anyone can trigger, and they answer a question nobody asks mid-request. They belong on a schedule that records that it ran, which is giro verify.
recon library Reconciliation needs a Source: something that calls your bank's API and returns normalised lines. That is an interface, and you cannot pass an implementation of one over HTTP. The adapter has to live in a process that can run your code.
obs library Telemetry is an interface the engine hands facts to, and an implementation of an interface cannot travel over HTTP. It is also a separate Go module: OpenTelemetry brings a dependency tree, and the engine having one dependency is a property worth keeping.
fx library Not an operation. It builds the two postings a conversion needs from the rate you state, and you commit them through the ordinary transactions endpoint. There is nothing for a route to do.
migrate library cli Schema changes take a session lock and must connect directly to Postgres rather than through a pooler. A serving process should not be able to change the schema, or to claim it changed one.

The line is the same in every row: the API is for moving money, and everything else is not. Setup, policy and inspection are operator work, done by something with a shell or a deployment, not by whatever is holding an HTTP connection.

The privilege is not what separates them: giro_app is granted update on the policy columns and always was, because the commit path needs the row. The channel is. So if you run giro as a service you still need a path to run giro account and giro verify — a job, a task runner, a deployment step. Serving it and operating it are two jobs.

08While it runs

Observing it

The checks below answer “is the book sound”. This answers “how is it behaving right now” — a different question, with a different failure, and neither detects the other.

Two lines, and nothing before that

An unobserved store computes nothing: the engine holds an interface, checks it for nil, and that is the entire cost of leaving this off.

Where the data goes is the standard OTEL_* environment, so giro has no telemetry configuration of its own to learn and none is a real setting.

A collector is optional — the SDK speaks OTLP straight to a backend. giro ships none: it is the upstream binary, already modular through its own builder, and writing another would be the same mistake as shipping an exchange client inside recon.

Spans nest, and that is the point

That turns “the commit took 45ms” into “40ms of it was waiting on world”, which is a different sentence with a different remedy.

Every deposit takes a row lock on world, so it is the hottest row in the system by construction — the wall this design meets first. giro.lock.wait climbing is what says to split it per counterparty. Nothing outside the engine can measure it: from the caller's side a contended commit and a slow one are identical.

More than one giro.commit.attempt inside a commit means it lost a deadlock and started again. Sorted lock ordering is supposed to make that impossible, so it is a correctness signal wearing a performance signal's clothes — page on it.

A refusal is not an error

users:alice cannot spend money she does not have is the ledger working. It gets its own counter and a span event, never an error status.

Generic HTTP middleware folds a 422 into a 4xx error rate, and a correct ledger under ordinary load then looks like a system in trouble — with the further cost that the day something genuinely breaks, the signal is buried in the noise of customers being short of money.

So group by reason, because the reasons have different owners:

insufficient_fundsProduct. A rise is a behaviour or pricing change.
unknown_assetA bug in a caller. Should sit flat at zero.
unexpected_creditA cost line leaning the wrong way — a loss booked as a gain. Look at this.
contention_exhaustedGave up after the retry limit. Page.

No metric is labelled by an account

A ledger's most natural label is an address, and addresses are unbounded. users:alice as a label is one time series per customer, which is how a metrics backend dies — discovered in production, usually during the incident the dashboard was built for.

Goes on
ledger, asset, reasonmetrics and spans
account addressesspans only

A span exists per request rather than per series, so which account was this stays answerable at three in the morning without producing a million time series to answer it. A test walks every emitted metric and fails if an address reached a label; another asserts cardinality is a function of configuration and never of traffic.

The consequence worth deciding before it leaves your network: a span attribute now carries customer identifiers. The collector config ships a processor, commented out, that drops them at the boundary — the trace keeps the shape of the commit and the lock timing, and loses whose money it was.

09Running it

Operating

Seven checks, none on the write path, each reporting what it examined. Two more run when you say what counts as stale, because neither window has a default anyone else can choose for you.

Alert on two conditions

Findings above zero is the one everybody writes. The absence of a run is the one that matters when the scheduler dies, because a detector that stopped running looks exactly like a book with nothing wrong.

giro verify --last --max-age=25h fails if a check has stopped, so a monitor treats it the same way: run it, look at the exit code.

Connect as a role that cannot alter a table

A table's owner outranks its own triggers, so serving as the owner makes every guard advisory. Three roles, each with one job: the owner migrates and nothing else; giro_app cannot log in and exists to hold the grants; giro_service logs in, owns nothing, and inherits only what the application needs. just db-app-role creates both.

One variable, two environments. Everything reads DATABASE_URL; the migration step is its own job and runs with the owner in its environment, so the owner's credential is never present where requests are served.

giro serve warns at boot if it can disable its own guards, and refuses to start against a schema it does not match. just privileges asks the database what the serving connection can actually do rather than trusting the config.

Behind a transaction pooler

The runtime takes no session locks, so it pools cleanly. Two conditions: migrations must connect directly, because a session advisory lock provides no mutual exclusion through a pooler, and the pooler must support prepared statements.

What to page on

conservation, log and projection mean the ledger is wrong about itself, which is the thing it exists to make impossible. The rest mean the world and the book disagree, or somebody needs to decide something. Those are morning work.
